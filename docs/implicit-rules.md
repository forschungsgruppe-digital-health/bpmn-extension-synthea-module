# BPMN → Synthea: Conversion Rules

Starting point: an arbitrary BPMN diagram (modeled with the `synthea:` extension) exists and needs to be converted into a Synthea GMF `.json` module.

Core problem: several Synthea states share the same BPMN element (e.g. a `Task` can be a `Procedure`, an `Observation` or a `MedicationOrder`). The mapping tables below therefore list, per BPMN element, the candidate Synthea states plus the **signal** the converter uses to decide between them — for a task that is the explicit `synthea:StateTypeConfig`.

---

## A. The `synthea:` extension

`synthea:` is the only extension this repository ships (details in `extension/model/synthea.json`). It supplies the execution semantics and the state type: delay values, guard condition, probabilities, encounter grouping, attribute links, and the explicit `StateTypeConfig` that says which Synthea state an element is. It answers "what is this state and how does it behave."

Two related extensions are separate projects and are not part of this repository: `fhirmap:` (which FHIR resource a state produces) and `term:` (the clinical code of a state). The converter does not need `fhirmap:` — the state type always comes from `StateTypeConfig` or from the element kind — and it still reads `term:coding` as an *optional* input for the `codes` field (see "Clinical codes" below).

**`synthea:` in detail** — entirely custom-designed for this project, since none of this data is clinical:

| Type | Attributes | Sits on | Why it's needed |
|---|---|---|---|
| `DelayConfig` | `delayShape`, `delayValue`, `delayValueHigh`, `delayUnit` | Timer intermediate event | carries Synthea's exact/range shape, which BPMN timers don't natively express. `delayValue` is the primary number (the `EXACT` value, or the `RANGE` low); `delayValueHigh` is the second number, meaningful only for `RANGE` (high) — checked by lint rule `delay-range-requires-high-value`, and the properties panel only shows the field at all when `delayShape="RANGE"`. Synthea's v2 `distribution` syntax (`GAUSSIAN`/`UNIFORM`/`EXPONENTIAL`) is deliberately not modeled: v1 `RANGE` already covers the project's needs (and samples uniformly per the Synthea wiki), so a second, redundant syntax for the same thing was out of scope |
| `GuardConfig` | `allow` | Exclusive gateway | distinguishes a *polling* gateway (Guard) from a one-shot branching gateway, and carries the actual gate condition. No `reevaluate` field — Guard always re-checks on the module's global simulation tick, not a per-instance interval (no such field exists in Synthea, so a field for it was deliberately not added) |
| `SubmoduleConfig` | `submodule` | Call activity | pins down that a call activity is specifically a Synthea submodule reference — no return-mapping field exists in Synthea, continuation after the submodule just follows the calling state's own `transition` |
| `ProbabilityConfig` | `probability`, `probabilityAttribute`, `probabilityDefault` | Sequence flow | BPMN has no native probabilistic branching — this is the only way to express `distributed_transition` weights |
| `EncounterContext` | `requiresEncounterContext`, `encounterId`, `wellness`, `encounterClass`, `reason` | Task / EndEvent / SubProcess / Intermediate event (any state-bearing flow node); still also available on TextAnnotation | marks that a state belongs to a given encounter (`encounterId` groups all member states of one encounter instance) and whether that encounter is a wellness encounter. `Encounter`/`EncounterEnd` are no longer drawn as their own states at all — `tools/bpmn2gmf` derives each `encounterId` group's span and synthesizes them for the JSON output; `wellness` must agree across every member of a group (see lint rule `wellness-consistent-within-encounter`). `encounterClass` mirrors Synthea's `Encounter.encounter_class` (`wellness`/`ambulatory`/`emergency`/`urgentcare`/`inpatient`/`outpatient`) — required by Synthea on every non-wellness encounter, must likewise agree across a group (see lint rule `encounter-class-consistent-within-encounter`); the properties panel only shows the field while `wellness` is unchecked. `encounterCodeSystem`/`encounterCode`/`encounterCodeDisplay` carry Synthea's required `Encounter.codes` (all three together, same on every member of a group — lint rule `encounter-code-complete-and-consistent`; `encounterCodeSystem` is the same URI `term:coding` uses). `reason` mirrors Synthea's `Encounter.reason` (either an attribute name or a `State_Name` referencing a prior `ConditionOnset`) — like `wellness`/`encounterClass`, it describes the encounter as a whole and belongs on the group's marker, not a separate type. See [ADR-0002](adr/0002-encounter-as-flow-node.md) (superseded) and [ADR-0003](adr/0003-encounter-context-implicit-scoping.md) (current) |
| `EncounterReference` | `targetEncounter` | Intermediate event (ConditionOnset/AllergyOnset) | Synthea's `target_encounter` field only exists on these two states, not on any other clinical state — see open points |
| `CounterConfig` | `attribute`, `action` (enum `increment`/`decrement`), `amount` | Task (`stateType="Counter"`) | mirrors Synthea's `Counter` state exactly; `action` is a required choice per the wiki, `amount` is optional (defaults to 1 in Synthea if unset here) |
| `SetAttributeConfig` | `attribute`, `value` **or** `valueAttribute` (copy another attribute's value; upstream `value_attribute`) | Task (`stateType="SetAttribute"`) | `value` covers Synthea's plain numeric/boolean/string assignment case; `valueCode`/`range`/`expression` (Synthea's other value-assignment options) are deliberately out of scope, matching the project's practice of leaving deeper clinical/simulation content (like ConditionOnset's terminology codes) to a dedicated mechanism rather than free-form fields on this type |
| `DistributionConfig` | `kind` (`EXACT`/`UNIFORM`/`GAUSSIAN`/`EXPONENTIAL`), `round`, and the parameters of the kind: `value` / `low`+`high` / `mean`+`standardDeviation` (+`min`,`max`) / `mean` | Task (`stateType="SetAttribute"`), alternative to `value` | a value drawn from a distribution, emitted as `distribution: {kind, round, parameters}` exactly as in the upstream lung cancer module (length of stay). The States wiki documents this `distribution` format only for `Delay`/`Procedure` (v2) — on `SetAttribute` it is attested by the upstream module, not by the wiki. A Delay or Procedure duration given as a distribution is still not modeled (v1 `range` covers it) |
| `SymptomConfig` | `symptom` | Task (`stateType="Symptom"`) | the symptom name Synthea tracks (required; never parsed from the label) |
| `ObservationConfig` | `category` (enum of the HL7 observation categories: `vital-signs`, `laboratory`, `procedure`, `imaging`, `survey`, `exam`, `therapy`, `social-history`) | Task (`stateType="Observation"`) | Synthea's required `Observation.category` |
| `ValueConfig` | `valueShape` (`EXACT`/`RANGE`), `value` (the exact value, or the low end), `valueHigh` (RANGE only), `unit`, `decimals` | Task/Intermediate event/End event with `stateType` `Observation`, `Symptom`, `Death` or `Procedure` (there: the optional `duration`, always with `unit`) | mirrors Synthea's exact/range choice, same shape as `DelayConfig`. `Observation`: `unit` is a field of the state, `decimals` goes into `range`; `Symptom`: no unit; `Death`: `unit` (a unit of time) goes *inside* `exact`/`range`, scheduling the death in the future while the module goes on (lint rule `value-range-requires-high-value`) |
| `ReportObservation` | `code`/`codeDisplay` (LOINC), `category`, `unit`, then exactly one of: `valueShape`/`value`/`valueHigh`/`decimals` (exact or range), `valueCodeSystem`/`valueCode`/`valueCodeDisplay` (coded value), `vitalSign` | Task (`stateType="DiagnosticReport"`), repeatable | one entry of a `DiagnosticReport`'s required `observations` list (a lab panel's single values). The three value forms are the ones the upstream modules use (range 100×, coded value 22×, vital sign 14× in `lung_cancer.json`/`anemia_sub.json`). Values are a modeling decision, not derivable from the panel's LOINC code. `number_of_observations` (not in the States wiki, inconsistent upstream) is not modeled |
| `MedicationConfig` | `administration` (Boolean) | Task (`stateType="MedicationOrder"`) | Synthea's optional `administration`: the medication is given during the encounter, not just prescribed. The export then marks the order as inpatient and refers to a Medication resource; without it the order is "community" |
| `CarePlanActivity` (repeatable) | `code`, `codeDisplay` (SNOMED CT, the system is fixed) | Task (`stateType="CarePlanStart"`) | Synthea's optional `activities`: the codes that describe the care plan; they end up as `activity` in the CarePlan resource |
| `ImagingStudySeries` | `bodySiteCode`/`bodySiteDisplay` (SNOMED CT), `modalityCode`/`modalityDisplay` (DICOM-DCM), `instanceTitle`, `sopClassCode`/`sopClassDisplay` (DICOM-SOP), `minInstances`/`maxInstances` (optional) | Task (`stateType="ImagingStudy"`), repeatable | Synthea's required `series` of an `ImagingStudy`, one image kind per series; the code systems are implied by the field |
| `AssignToAttributeConfig` | `attribute` | Task/Intermediate event/TextAnnotation, semantically only `ConditionOnset`/`AllergyOnset`/`MedicationOrder`/`CarePlanStart`/`Device` | Synthea's `assign_to_attribute` is not its own state type — it's an optional field on exactly these five states, letting a later End state reference back via the attribute instead of relying on path order (see `ReferencedByAttributeConfig` below and open points on ambiguous start/end pairing) |
| `ReferencedByAttributeConfig` | `attribute` | Task/EndEvent/Intermediate event/TextAnnotation, semantically only `ConditionEnd`/`AllergyEnd`/`MedicationEnd`/`CarePlanEnd`/`DeviceEnd`/`Death` | the counterpart to `AssignToAttributeConfig`: Synthea's `referenced_by_attribute` is documented on exactly these six states (confirmed against the wiki) as one of several alternative ways to point back at the entity a corresponding `*Onset`/`Order`/`Start` state recorded via `assign_to_attribute` — instead of matching by `codes` or relying on path order |
| `Condition` | `conditionType` (enum, 20 values), plus per-type fields: `attribute`/`operator`/`value` (Attribute), `gender` (Gender), `race` (Race), `category` (Socioeconomic Status), `quantity`/`unit` (Age, + `operator`), `year`/`month` (Date, + `operator` — Synthea's fuller `date` object with day/hour/minute/second/millisecond isn't modeled, only the year/month case), `symptom` (Symptom, + `operator`/`value`), `referencedAttribute` **or** `codeSystem`/`code`/`codeDisplay` (Observation + the 4 Active-\* types, Observation also + `operator`/`value`; the code triple is the alternative to the attribute, never both, and all three parts are required — Basics wiki: "a `system`, `code`, and `display` are required fields". `codeSystem` holds the same URI `term:coding` uses, `tools/bpmn2gmf` maps it to `LOINC`/`SNOMED-CT`/`RxNorm`), `vitalSign` (Vital Sign, + `operator`/`value`), `priorStateName`/`since` (PriorState, + `quantity`/`unit` reused for Synthea's `within: {quantity, unit}` — not a plain string, matching the shape Age already uses those fields for); `True`/`False` need no extra field; `conditions` (self-referencing, `isMany`: a list of nested `Condition` elements — `And`/`Or`, or `At Least`/`At Most` alongside `minimum`/`maximum`); `negate` | nested inside `GuardConfig.allow` or `ConditionConfig.condition`, and — for combinator types — inside another `Condition.conditions` (one level deep in the properties panel, unlimited in the schema) | a flat/recursive structured mirror of Synthea's logic vocabulary (see [Logic wiki](https://github.com/synthetichealth/synthea/wiki/Generic-Module-Framework:-Logic)) — deliberately not free text, since free text can't be reliably auto-translated back into a GMF condition object. Every field beyond `conditionType` is only meaningful for its own type(s); the properties panel enforces this by only showing the relevant subset per `conditionType` (`CONDITION_FIELDS_BY_TYPE` in `SyntheaPropertiesProvider.js`), recursively for nested sub-conditions too. `codes`-based entity matching on Observation/Active-\* is supported through the `codeSystem`/`code`/`codeDisplay` triple (decision 8 of the bpmn2gmf concept; first needed by the anemia module's hematocrit check). **`negate` is a bridging construct, not a literal Synthea field** — confirmed against the wiki that Synthea has no negate/not boolean at all; negation is expressed only by wrapping a condition in a separate `Not` condition object (`{"condition_type": "Not", "condition": {...}}`). `negate="true"` on a flat `synthea:Condition` is defined to be semantically equivalent to that `Not` wrapper around the same condition with `negate` stripped — `tools/bpmn2gmf` (not yet built) MUST perform this expansion on export, or the negation is silently lost |
| `ConditionConfig` | `condition` (nested `Condition`) | Sequence flow | carries the structured condition for a `conditional_transition` branch; the native BPMN `conditionExpression` on the same flow stays as the human-readable label only |
| `StateType` / `StateTypeConfig` | `stateType` (enum of all ~30 GMF state names), and the code of the state: `codeSystem` (URI), `code`, `codeDisplay` | any state-bearing flow node (Task / Event / Gateway / Sub-process) | the explicit tag for "which GMF state is this", and, on the same element, which clinical code it carries (`codes` in the JSON). The panel offers the code fields only for state types that carry one |

**A note on `synthea:StateType`/`StateTypeConfig`:** this is the explicit, closed-vocabulary tag for "which GMF state is this". For start events, end events (as `Terminal`), gateways, timer events and call activities the converter can infer the type from the element kind; for a task, a sub-process and every other event it is **required** (`STATE_TYPE_REQUIRED` otherwise). The properties panel offers, per element, only the types the converter accepts there (start event `Initial`; end event `Terminal`/`Death`; exclusive gateway `Simple`/`Guard`; call activity `CallSubmodule`; sub-process `DiagnosticReport`/`MultiObservation`/`CallSubmodule`; tasks and other events all types). Which `synthea:` type may sit on which element is in [`extension-matrix.md`](extension-matrix.md).

### Clinical codes

The clinical code of a state (`codes` in the GMF JSON: SNOMED CT, LOINC, RxNorm) sits on the element's `synthea:StateTypeConfig` as `codeSystem` (the system URI, e.g. `http://snomed.info/sct`), `code` and `codeDisplay`. One code per state; the converter turns the URI into Synthea's name (`SNOMED-CT`, `LOINC`, `RxNorm`) and keeps only the systems the state type accepts. The Encounter code is separate: it lives in `synthea:EncounterContext` and belongs to the generated Encounter state. As an optional input the converter also reads a `term:coding` from the separate terminology extension.

Which code system a state accepts (what the converter keeps, `codes.mjs`):

| Vocabulary | States | Note |
|---|---|---|
| SNOMED CT | ConditionOnset/End, Procedure, ImagingStudy, CarePlanStart/End, Device/DeviceEnd, SupplyList, Encounter, Observation `value_code` | largest share of coverage |
| SNOMED CT or RxNorm | AllergyOnset/End | substance codes may be either; reactions always SNOMED CT |
| LOINC | Observation/MultiObservation/DiagnosticReport | the observation *type*, distinct from its coded value |
| RxNorm | MedicationOrder/MedicationEnd | |
| NUBC | `EncounterEnd.discharge_disposition` | a fourth, narrower vocabulary outside the original three-system scope |

**Valid `unit` values** (per the Basics wiki): any `unit` field tied to a time/age quantity — `DelayConfig.delayUnit`, `Condition.unit` (used by both `Age` and `PriorState`) — should be one of `years`, `months`, `weeks`, `days`, `hours`, `minutes`, `seconds`. These fields are free text in the schema (not an enum), since Synthea's `Measurement`-category units (e.g. for `Vital Sign`/`Observation` values) accept an arbitrary string instead — so this is a documentation convention for modelers, not something the panel enforces.

## B. Nodes (Flow Nodes)

| BPMN element | Candidate Synthea state(s) | Disambiguation signal | What gets carried into the JSON |
|---|---|---|---|
| Start event | `Initial` | unambiguous, no disambiguation needed | nothing further, plain entry point |
| End event | `Terminal` **or** `Death` | `synthea:StateTypeConfig.stateType="Death"` selects `Death`; without it the end event is `Terminal` | for `Death`: an optional time span (`ValueConfig`), the cause as a reference to a preceding `ConditionOnset` (`ReferencedByAttributeConfig`) or a code |
| Exclusive gateway **with** `synthea:GuardConfig` | `Guard` | extension attribute `allow` present | `allow` (nested `synthea:Condition` element: `conditionType`/`attribute`/`operator`/`value`); Guard always re-checks on the module's global tick, no per-instance poll interval (no such field in Synthea); like any other state, can also carry a `distributed_transition`/`conditional_transition` (officially documented, see the Age_Guard example) |
| Sequence flow with no intermediate node (a bare connection between two activities with no element of its own) **or** exclusive gateway **without** `synthea:GuardConfig` | `Simple` | no element present (plain pass-through) **or** gateway without `GuardConfig` — both represent a stateless node that only carries a transition | for the plain pass-through: just `type: "Simple"`; for the gateway variant: the transition logic of the outgoing flows (`direct`/`conditional`/`distributed`, see table C) is attached directly to this Simple state |
| Timer intermediate event | `Delay` | unambiguous (only Delay uses timer events) | `synthea:DelayConfig`: `delayShape` (`EXACT`/`RANGE`) determines the JSON shape; `delayValue`/`delayValueHigh`/`delayUnit` (the second value only meaningful for `RANGE`, see Section A) |
| Call activity | `CallSubmodule` | unambiguous (only CallSubmodule uses call activities) | `synthea:submoduleRef` → `submodule`; continuation after the submodule follows the calling state's own `transition` (no return-mapping field in Synthea) |
| Task | `MedicationOrder`, `Procedure`, `ImagingStudy`, `Observation`, `ConditionOnset`, `AllergyOnset`, `CarePlanStart`, `Device`, `SetAttribute`, `Counter`, `Symptom`, `VitalSign`, `MedicationEnd`, … (every state type except the structural ones) | the explicit `synthea:StateTypeConfig.stateType` — **required**, there is no inference for a task | the fields of that state type (see the `synthea:` table in Section A); the `requiresEncounterContext` flag; for ConditionOnset/AllergyOnset also `synthea:EncounterReference.targetEncounter`. The real lung-cancer pathway models every ConditionOnset as a Task |
| Sub-process | `DiagnosticReport`, `MultiObservation`, or `CallSubmodule` | the explicit `stateType` — required; any other type is `STATE_TYPE_MISMATCH` | **one state**: for `DiagnosticReport` the contained measurements as `synthea:ReportObservation` entries; for `CallSubmodule` a `synthea:SubmoduleConfig` (how drafts and the mihub models use sub-processes for separate modules). The elements drawn inside are **not** converted (note `SUBPROCESS_CONTENT_IGNORED`). `Physiology` is not implemented. A sub-process with ordinary sequential content has to be flattened (Modeling Guide, section 3) |
| Intermediate event (non-timer, e.g. a generic intermediate event) | `ConditionOnset`, `ConditionEnd`, `AllergyOnset`, `AllergyEnd`, and any other state type | the explicit `stateType` — required; a timer event is `Delay` without one | the fields of that state type; `synthea:EncounterReference.targetEncounter` if present — **only** valid on ConditionOnset/AllergyOnset (see Section E). `ConditionOnset`/`AllergyOnset` may equally be modeled as a `Task`; the JSON output is identical either way |
| Text annotation | *(none)* | not converted — the converter ignores annotations; the properties panel offers no `synthea:` groups on them | nothing. Put the state on the task or event itself |
| *(not a BPMN element — synthesized)* | `Encounter`, `EncounterEnd` | *n/a — these are not drawn at all.* Every clinical state belonging to the encounter carries `synthea:EncounterContext` with a shared `encounterId` (see Section A and [ADR-0003](adr/0003-encounter-context-implicit-scoping.md)) | `tools/bpmn2gmf` takes the first-to-last span of each `encounterId` group (in sequence-flow order) and synthesizes the `Encounter`/`EncounterEnd` JSON states around it; `wellness` comes from the group's (consistent) `EncounterContext.wellness` value |

### B.1 Text annotations (no longer used for states)

Earlier concepts let a `TextAnnotation` stand for states without a FHIR resource (`MedicationEnd`, `CarePlanStart`/`CarePlanEnd`, `Device`/`DeviceEnd`, `SupplyList`, `VitalSign`, `Symptom`, `SetAttribute`, `Counter`) and recognised them through a resource type. That is gone: every such state is a `Task` (or event) with an explicit `synthea:StateTypeConfig`, and a text annotation is only a comment. The start/end pairing of `MedicationOrder`/`MedicationEnd`, `CarePlanStart`/`CarePlanEnd` and `Device`/`DeviceEnd` works through `AssignToAttributeConfig`/`ReferencedByAttributeConfig` (Section E).

## C. Edges (Sequence Flows / Transition Type)

| Sequence flow configuration | Synthea transition type | What gets carried into the JSON |
|---|---|---|
| Exactly one outgoing flow, no condition, no probability | `direct_transition` | target state name |
| Multiple outgoing flows, all carrying `synthea:ProbabilityConfig probability="..."` | `distributed_transition` | list of `{transition, distribution}`; check the sum (see lint rule `probability-sum-valid`) |
| Multiple outgoing flows with `synthea:probabilityAttribute` instead of a fixed value | `distributed_transition` with a "named distribution" | `{transition, distribution: {attribute, default}}` |
| Multiple outgoing flows with a `conditionExpression` (native BPMN) **and** `synthea:ConditionConfig.condition` | `conditional_transition` | list of `{condition, transition}` in flow order — `condition` comes from the structured `synthea:Condition`, **not** from parsing the free text of `conditionExpression`: free text can't be reliably translated back automatically. `conditionExpression` stays only as a human-readable on-diagram label |
| One flow with no condition, modeled as the BPMN default flow within a conditional group | last `conditional_transition` element with no `condition` (implicit fallback) | target state with no condition field |
| Conditional flows **without** a default flow | `conditional_transition` with no fallback → Synthea implicitly transitions to `Terminal` when nothing matches | the converter has to **synthesize** this implicit Terminal transition, since it isn't visible in the BPMN |
| Last flow of a `distributed_transition` group without its own `probability` value | implicitly receives the remainder up to 1.0 | `distribution` = 1.0 − sum of the others |
| Conditional flows whose targets are probability gateways (with `--fuse-gateways`) | `complex_transition` | list of `{condition?, transition}` / `{condition?, distributions: [{transition, distribution}]}`; the entry without `condition` is the default flow and comes last. Only an output form: the diagram stays a condition gateway followed by probability gateways. |
| *(no BPMN pattern defined)* | `lookup_table_transition` | Like `distributed_transition`, but each branch's probability comes from an external CSV (`lookup_table_name`) keyed by patient attributes (race/ethnicity/gender/age/smoker/…) instead of a fixed number — needs `transition`, `default_probability`, `lookup_table_name` per branch. No `synthea:` extension attribute or flow convention models this yet |
| *(no BPMN pattern defined)* | `type_of_care_transition` | A fixed 3-way branch to `ambulatory`/`telemedicine`/`emergency` target states, weighted by insurance status and simulation year (via `telemedicine_config.json`) rather than any patient attribute a BPMN condition could reference — no `synthea:` extension attribute or flow convention models this yet |

## D. Gateway Chains and Complex Logic

Several consecutive `Simple` states (from chained gateways without `GuardConfig`) are the regular way to represent nested condition/probability logic — this is the officially documented purpose of `Simple` ("chain conditional or distributed transitions to represent complex logic"). `complex_transition` (combining conditional and distributed in a single state) is only an optional compaction of this, not a prerequisite — a converter may optionally use it to collapse two chained Simple states into one, but it isn't required for correctness.

## E. Open Points

- ~~**Annotation disambiguation without a FHIR resource**~~ — **moot**: states are never recognised from a text annotation any more (see Table B.1); every state carries an explicit `stateType` on its task or event.
- ~~**`allow` condition is flat only**~~ — **resolved**: `synthea:Condition` now covers all 20 of Synthea's `condition_type` values, including the combinators. `conditions` is a genuinely self-referencing `isMany` property (a `Condition` can hold a list of nested `Condition` elements), used by `And`/`Or` (both take the list, no other field) and `At Least`/`At Most` (list plus `minimum`/`maximum`). `negate`/`Not` remains the flat bridging construct it always was (see Section A) — it was never part of this gap. Two deliberate simplifications remain: (1) the properties panel only offers editing for `MAX_NESTED_CONDITIONS = 3` sub-conditions per combinator, one level deep — the schema itself has no such limit, so deeper or wider nesting still round-trips correctly if hand-authored in the XML, the panel just won't build it for you; (2) `guard-allow-requires-condition`/`negate-requires-condition` check presence of `conditionType` (plus, for combinators, a non-empty `conditions` list) rather than every type's exact required fields — a combinator with the right shape but semantically-empty sub-conditions (e.g. `And` containing two `Condition` elements with no `conditionType` of their own) isn't caught, since validating that recursively was judged disproportionate to the risk for a single-author project.
- **Start/end pairing via annotations**: `MedicationOrder`/`MedicationEnd`, `CarePlanStart`/`CarePlanEnd`, `Device`/`DeviceEnd` (and `ConditionOnset`/`ConditionEnd`, `AllergyOnset`/`AllergyEnd`) are, by default, paired only by order in the path, not by an explicit ID reference — ambiguous with several similar elements in the same module. (`Encounter`/`EncounterEnd` no longer have this problem — resolved via `EncounterContext.encounterId` grouping, see ADR-0003.) The `AssignToAttributeConfig`/`ReferencedByAttributeConfig` pair now models both halves of Synthea's own `assign_to_attribute`/`referenced_by_attribute` mechanism, so a modeler *can* fully disambiguate a specific pair. Nothing enforces that they actually get used — falling back to path order is still valid — but if a `ReferencedByAttributeConfig.attribute` is set, lint rule `referenced-by-attribute-matches-assign` now checks that a matching `AssignToAttributeConfig.attribute` exists somewhere in the same process (name match only, not flow-order-aware).
- **Missing transition types**: `lookup_table_transition`, `type_of_care_transition` are now listed in Table C (with their real field requirements, verified against the Transitions wiki) but still have no BPMN pattern — a modeler has no way to express either one today. Neither is likely to matter for this project's pathways (`type_of_care_transition` picks ambulatory/telemedicine/emergency by insurance+year, not a modelable clinical condition; `lookup_table_transition` needs an external CSV this project doesn't have a slot for). (`complex_transition` is no longer a blocker, see Section D.)
- **ConditionOnset/AllergyOnset and `target_encounter`**: `synthea:EncounterReference.targetEncounter` applies exclusively to `ConditionOnset`/`AllergyOnset` (a reference to a possibly-future encounter) — **not** to `ConditionEnd`/`AllergyEnd` or any other clinical state, which instead get attached automatically to whichever `Encounter` was most recently processed (`current_encounter`). **Resolved**: enforced by lint rule `encounter-reference-requires-condition-or-allergy-context` (SYN-18).
- **`targetEncounter`'s value is unspecified**: Synthea's real `target_encounter` must be a literal `State_Name` of a future/concurrent `Encounter` state in the generated JSON — but this project no longer draws `Encounter` states at all (ADR-0003); they're synthesized by `tools/bpmn2gmf` from `EncounterContext.encounterId` groups, under a state name the converter itself invents. Nothing yet specifies what a modeler should put in `targetEncounter` to reference one of these not-yet-named, synthesized states. Most likely resolution: `targetEncounter` should hold the target group's `encounterId` (the one identifier a modeler actually has), with `tools/bpmn2gmf` resolving it to whatever `State_Name` it assigns that group's synthesized `Encounter` — but this convention isn't decided or documented anywhere yet.
- ~~**`submodule` path format is unconfirmed**~~ — **resolved, and the first decision was wrong (corrected after running the modules in Synthea v4.0.0)**: files directly in the modules directory are run as modules of their own for every patient; only files in a *subdirectory* are submodules (`Module.walkModuleTree`: `submodule = !file.getParent().equals(modulesPath)`), and `CallSubmodule` names them by path. `tools/bpmn2gmf` therefore writes a module that nobody calls to the top and the modules it calls to a subdirectory named after it, and prefixes every `submodule` with that path (`synthea_lung_cancer/anemia_submodule`); the bare names in `SubmoduleConfig.submodule` stay as they are in the diagrams. - ~~**`encounterId` can't express two encounters converging on shared states**~~ — **resolved for the common case**: real Synthea has no version of this problem, because encounter membership is resolved dynamically at simulation time (`current_encounter`, tracked on the person, not declared per state) — a shared state simply attaches to whatever encounter is already active when it's actually processed, regardless of which upstream path led there. Confirmed directly against the real `anemia_sub.json`: `Administer_Medications`/`Iron_Supplement`/`Vitamin B12 Booster` carry **no** `encounter_class` at all in the upstream module, even though they're reached from both `Anemia_Encounter`'s workup and, via `Consult_Referral_to_Experts_Encounter`, the blood-panel branch — leaving them untagged lets them correctly inherit whichever encounter is still open on that specific path, exactly matching the dynamic runtime behavior. Our own `anemia-submodule.bpmn` previously tagged `Iron_Supplement`/`Vitamin B12 Booster` with a fixed `encounterId="Anemia_Encounter"` (diverging from the upstream source, and imprecise for the referral path) — fixed by removing `EncounterContext` from both, matching upstream. **General rule:** a state reachable from more than one `encounterId` group should usually be left untagged (`requiresEncounterContext` unset) rather than forced onto one path's id, as long as every reaching path has *some* encounter already open — it isn't a gap needing tooling support, just a modeling default to prefer. The residual, rarer case this doesn't cover: a shared state that must itself carry *different* `wellness`/`encounterClass` values depending on path (not just bookkeeping, an actual product requirement) — there, the real fix is duplicating the state once per path in the diagram, each copy tagged independently; a second `encounterId` field wouldn't help, since `tools/bpmn2gmf` would still have to emit two separate generated states for the one diagram node either way.
